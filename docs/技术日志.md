## 补充一：`std::string::npos` 是什么

`npos` = `size_t` 能表示的最大值（`18446744073709551615`）。`find` 找不到时**返回它**——因为 `find` 返回 `size_t`，没法返回 `-1`，所以拿最大值当"没找到"的标记。

```cpp
size_t pos = path.find_last_of("/\\");
if (pos == std::string::npos) {
    // 路径里没有分隔符，整个 path 就是文件名
} else {
    std::string name = path.substr(pos + 1);
}
```

**这个判断不能漏。** 文件名叫 `yolov8.rknn`、没有路径时 `pos` 就是 `npos`，此时 `pos + 1` 绕回 0，`substr(0)` 刚好是对的——纯属运气。换个写法就错，所以必须显式判断。

## 补充二：`memset` 到底怎么用

```cpp
DetResultList list;
memset(&list, 0, sizeof(list));    // 整块清零：count = 0，results 全 0
```

**毕设里真正会用到的两处：**
1. 初始化 RKNN 的接口结构体：`rknn_input input; memset(&input, 0, sizeof(input));` —— 这类 C 风格结构体字段多，逐个赋值容易漏
2. 清零图像缓冲区

**三条铁律：**
- 第二个参数是**按字节填**：`memset(p, 1, 4)` 得到的不是 1，是 `16843009`
- 第三个参数是**字节数**，不是元素个数
- **含 `std::string` / `std::vector` 的结构体绝对不能 `memset`** —— 会把它们内部的指针抹成 0，之后一用就崩

现代 C++ 能用 `= {}` 就别用 `memset`；只在处理 C 风格 buffer 时才用它。

## 补充三：10/29 晚踩的两个坑

### 1. 为什么 `remove_if` 里不能直接写成员函数

```cpp
bool isUnmeasured(const DetResult& r) { return r.depth < 0; }    // 成员函数
std::remove_if(results_.begin(), results_.end(), isUnmeasured);   // ❌ 编译不过
```

报错：

```
error: must use '.*' or '->*' to call pointer-to-member function
```

**原因**：成员函数隐含一个 `this`，所以它的类型不是「函数」，而是「**成员函数指针**」——`bool (DetFrame::*)(const DetResult&)`。这种指针光有地址不够，还得知道**对哪个对象调用**，所以不能直接当函数传。

**修法**：加 `static`

```cpp
static bool isUnmeasured(const DetResult& r) { return r.depth < 0; }
```

静态成员函数没有 `this`，类型退化成普通函数指针 `bool (*)(const DetResult&)`，就能直接传了。

> `static` 成员函数的唯一用途就是这个：**需要它不带对象的时候**。反过来说，只要函数里碰了成员变量，就不能加 `static`。

### 2. `std::clamp` 返回新值，不改原值

```cpp
std::clamp(r.left, 0, w);              // ❌ 什么都没发生，返回值被扔了
r.left = std::clamp(r.left, 0, w);     // ✅
```

`std::clamp` 的签名是 `const T& clamp(const T& v, const T& lo, const T& hi)`——它**算出一个新值返回**，根本不碰原变量。所以外面那层 `if (left < 0 || left > w)` 也不需要，clamp 自己两个方向都管。

**危险之处：这种错误编译零警告、能跑、不崩，只有断言（或肉眼看结果）才抓得到。**

以后凡是调完一个函数就把它扔了，先问自己一句：**「它是不是原地改的？」** 名字带 `set_` / `to_` 的通常原地改；`std::` 里的算法和数学函数（clamp / min / max / abs）几乎全是**返回新值**。

## 问题 1 答案：`DetResult` 对应 RKNN 的哪个结构

对应 `rknn_model_zoo/examples/yolov8/cpp/postprocess.h` 里的 **`object_detect_result`**。

RKNN 原文（照抄，未改动）：

```c
typedef struct { int left; int top; int right; int bottom; } image_rect_t;   // 在 utils/common.h

typedef struct {
    image_rect_t box;          // 四个坐标打包成了一个 box
    float prop;
    int   cls_id;
} object_detect_result;

typedef struct {
    int id;                                 // 帧号，我没有这个字段
    int count;
    object_detect_result results[OBJ_NUMB_MAX_SIZE];   // OBJ_NUMB_MAX_SIZE = 128
} object_detect_result_list;
```

**字段对照：**

| 我的 `DetResult` | RKNN `object_detect_result` | 说明 |
|---|---|---|
| `cls_id` | `cls_id` | 一样 |
| `prop` | `prop` | 一样 |
| `left / top / right / bottom` | `box.left / box.top / box.right / box.bottom` | **RKNN 是嵌套在 `box` 里，多一层** |
| `depth` | —— | **RKNN 完全没有，是测距模块自己加的** |

**实测内存布局**（编译 `sizeof` / `offsetof` 得到）：

```
sizeof(object_detect_result) = 24     box=0  prop=16  cls_id=20
sizeof(DetResult)            = 28     cls_id=0  prop=4  left=8  depth=24
差 4 字节 —— 正好就是 depth 那一项
```

**两处必须记住的差别：**

1. 访问要写 `r.box.left`，**不是** `r.left`。套用 RKNN 结构时少写一层会编译报错。
2. `results` 上限是 **128**（`OBJ_NUMB_MAX_SIZE`），不是我练习里写的 64；它还多一个 `int id`（帧号）。
   实测 `sizeof(object_detect_result_list)` = **3080** = id(4) + count(4) + 128 × 24。

## 问题 2 答案：为什么用 `depth = -1` 而不用 `0`

三条理由，**第三条是真正致命的**：

1. **`0` 是合法的测量值，负数不是。** 距离不可能为负，所以负数天然能当"无效"标记，永远不会和真实测量混淆。

2. **一条判据就够。** `depth >= 0` 就是有效，`depth < 0` 就是无效。不需要额外加一个 `bool valid` 字段，结构体也不膨胀。

3. **SGBM 立体匹配失败的像素，视差就是 0。** 这些像素换算出来的深度可能是 0 或极小值。如果用 `0` 表示"未测距"，就**分不清"没测"和"测得 0 米"**——而"0 米"在预警逻辑里是最高危险等级，会**直接误报警**。

这就是我在 day05 里让你写 `findNearestIndex` 必须先 `if (depth < 0) continue;` 的原因。

## 问题 3 答案：哪几个函数该加 `const`

**你的答案是对的：`countByClass` 和 `findNearestIndex`。**

判断标准一句话：**这个函数会不会改动对象的成员变量？** 不动的才能标 `const`。

| 函数 | 改对象吗 | 加 `const` 吗 |
|---|---|---|
| `countByClass` | 否，只读 | ✅ 加 |
| `findNearestIndex` | 否，只读 | ✅ 加 |
| `clampToImage` | 是，改框坐标 | ❌ 不加 |
| `removeUnmeasured` | 是，删元素 | ❌ 不加 |
| `buildFrame` | 特殊，见下 | —— |

**`buildFrame` 单独说**：它原来是"凭空造一帧返回"，既不读也不改任何已有数据。写进类里以后它只有两条路：

- 变成**构造函数** `DetFrame(std::vector<DetResult> v)`
- 变成**静态函数** `static DetFrame buildFake()` —— 静态函数没有 `this`，也就谈不上 `const`

真项目里这一帧是从 RKNN 推理结果来的，所以它更可能变成 `loadFromRknn()`，那个**是要改对象的**，不加 `const`。

**加 `const` 的实际好处**：标上之后，如果你在这个函数里手滑改了成员变量，**编译器直接报错**，不用等到跑起来才发现数据被改坏。等于免费请了个检查员。

这就是 `class DetFrame` 的第一个考点（day06 已经过掉了）。

## 补充四：10/30–10/31 踩的三个坑（继承与多态）

### 1. 不写 `virtual` 会静默跑错，不报错、不崩溃

这是这一块最贵的一课。同一段循环，两种情况：

```cpp
class Device2 {
public:
    /* 没有 virtual */ const char* name() const { return "Device2(基类)"; }
    int grab(int& id) { id = 0; return 1; }
};
class Camera2 : public Device2 {
public:
    /* 自己写了一份 */ const char* name() const { return "Camera2"; }
};

Device2* ds[2] = { &cam2, &vid2 };
for (int i = 0; i < 2; i++)
    std::cout << ds[i]->name() << "\n";     // 两次都打印「Device2(基类)」
```

**编译零警告、运行不崩溃、断言要是不写就永远发现不了。** 派生类里那份 `name()` 变成死代码。

原因：没有 `virtual` 时，`ds[i]->name()` 在**编译期**就按 `ds[i]` 的静态类型 `Device2*` 定死调 `Device2::name`。它压根不知道运行时指向的是 `Camera2`。

加上 `virtual` 之后，**上面这个循环一个字都不用改**，输出立刻变成 `Camera2` / `Video2`。

> 判断标准：**只要你会通过基类指针调用它，就必须是 `virtual`。** 派生类里对应写上 `override`，基类忘了标虚的话编译器会报 `marked 'override', but does not override`，等于给自己装了个警报器。

### 2. 虚函数是有代价的：`sizeof` 从 4 涨到 16

实测：

```
sizeof(Device2) = 4   字节（没有虚函数，只有一个 int id_）
sizeof(Device3) = 16  字节（有虚函数）
```

多出来的 12 字节里，**8 字节是虚函数表指针（vptr）**，剩下 4 字节是对齐补水。每个对象都带一个 vptr，运行时靠它找到属于自己类的那张函数地址表——这就是「动态绑定」的物理实现。

所以虚函数不是白给的：**对象变大、每次调用要多跳一次表**。这也是为什么 `std::vector` 之类的库类型不随便加虚函数。毕设里目标检测一帧 128 个结果，`DetResult` 就**绝对不能**带虚函数，否则结构体膨胀、还不能直接和 RKNN 的 C 结构体对拷。

### 3. 对象切片：`sizeof` 一样大，照样切

```cpp
class SliceB { public: int x; virtual void f() {} };   // sizeof = 16
class SliceD : public SliceB { public: int y; };        // sizeof = 16

SliceD d; d.x = 1; d.y = 2;
SliceB b = d;        // ← 切片发生在这一行
```

`d.y` **没了**。`b` 只是一个普通的 `SliceB`，它的 vptr 指向 `SliceB` 的表，调 `f()` 走的是 `SliceB::f`。

**注意那个陷阱**：`sizeof(SliceB)` 和 `sizeof(SliceD)` 都是 16（`y` 正好填进了基类 vptr 后面的 padding），**所以「大小一样」完全不能证明没切片**。切片是**类型**问题，不是大小问题。

三种会切片的地方，全都要避开：

| 写法 | 结果 |
|---|---|
| `Base b = derived;` | 切片 |
| `void f(Base b)` 按值传参 | 切片 |
| `std::vector<Base> v; v.push_back(derived);` | 切片 |
| `Base& r = derived;` | ✅ 不切 |
| `Base* p = &derived;` | ✅ 不切 |
| `std::vector<Base*> v;` 或 `vector<unique_ptr<Base>>` | ✅ 不切 |

**这就是为什么多态只能通过指针或引用。** 毕设里装输入源的容器必须是 `std::vector<std::unique_ptr<Device>>`，写成 `std::vector<Device>` 就全切了。

### 4. 基类一个虚函数都没有时，漏析构编译器一声不吭

```cpp
class BaseN { public: ~BaseN() {} };                        // 没有虚函数
class DerN : public BaseN { public: ~DerN() { /* 释放资源 */ } };

BaseN* p = new DerN();
delete p;              // ← 只跑 ~BaseN，~DerN 根本没执行
```

实测**零警告**。只有基类里已经有虚函数时，g++ 才会报：

```
warning: deleting object of polymorphic class type 'X' which has non-virtual destructor [-Wdelete-non-virtual-dtor]
```

两种情形都要记住，因为**最危险的是前一种：连警告都没有**。

验证办法（比看警告可靠）：给每个派生类加一个存活计数，构造 `+1`、析构 `-1`，最后断言它回到 0。

```cpp
static int g_camLive = 0;
CameraDevice::CameraDevice(int n) { ++g_camLive; }
CameraDevice::~CameraDevice() { --g_camLive; }
// ...
delete ds[0];
assert(g_camLive == 0);     // 非虚析构时这里会是 1
```

> `virtual` 的传染是**单向向下**的：基类析构标了 `virtual`，所有派生类的析构**自动**都是虚的，不用逐层写；反过来不成立，中间层自己加 `virtual` 对 `delete 基类指针` 无效。
